# 页面结构推导（需求 → 楼层 → 组件）

从需求 / 设计意图到代码之间有一层中观结构：**页面由哪些楼层组成、每个楼层用什么方式承载**。本文件管这一层；控件级细节（某个具体控件选哪个 O 组件、关键 props / slots）见 [component-cheatsheet.md](component-cheatsheet.md)，完整组件 API 见 [opendesign-components](../../opendesign-components/SKILL.md)。

**分界**：

| 层 | 管什么 | 文件 |
|----|--------|------|
| 中观层（本文件） | 楼层序列、楼层内容职责、楼层级承载选型（卡片栅格 / 表格 / 标签页…） | `page-structure.md` |
| 控件级 | 按钮 / 输入框 / 标签等具体控件的选用与 props / slots | [component-cheatsheet.md](component-cheatsheet.md) |

---

## 双入口分流：先看上游给了什么

动手推导前先检查输入材料，按两条入口分流：

**入口 A：上游已提供楼层规划 / 组件清单**（设计侧或需求侧已确认的材料，常见形态：楼层序列表、带功能编号的内容清单、组件选型表）→ **校验承接，不重推**：

1. 逐项核对材料完备性：楼层序列完整（含导航 / 页脚的站点框架）、每楼层有内容摘要与来源（功能编号或素材条目）、组件清单覆盖每个楼层。
2. 材料与页面目标冲突或有缺口（某楼层无内容来源、组件与内容形态错位）时，**只就冲突 / 缺口项向需求方提问补齐**，不推翻重推。
3. 承接通过后直接进入「楼层内组件选型」细化，跳过下述四步推导。

**入口 B：上游未提供**（只有需求描述 / PRD / issue）→ 按下面四步自推。

---

## 四步推导（入口 B）

### 第一步：提取设计输入

从需求材料提取四项关键信息，缺一先补齐再继续：

| 设计输入 | 来源 | 用途 |
|---------|------|------|
| 页面目标与成功指标 | 需求背景 / 目标 | 判定页面类型与楼层取舍的锚点 |
| 目标用户与场景 | 用户与场景描述 | 内容优先级与语气 |
| 功能模块清单（带编号） | 功能清单 / 功能详述 | 楼层与组件的需求可溯来源 |
| 目标设备 | 适配范围 / 约束 | 布局与响应式决策（PC / 多端） |

### 第二步：判定页面类型

按核心用户任务与内容形态对照典型页面范式表（下节）判定，可组合（如「首页 = 门户 + 列表聚合」）。判定结果决定楼层骨架与默认组件倾向。

### 第三步：楼层规划

产出楼层序列：**导航（站点框架）→ [Banner（可选）] → 楼层 1 … 楼层 N → 页脚（站点框架）**，每楼层标注内容摘要与来源功能编号。规划遵守两条取舍纪律：

1. **每个楼层都要有内容职责**：拒绝纯装饰 / 营销楼层——没有来源功能编号或真实素材可对应的楼层不进规划，信息密集型内容楼层优先。
2. **信息密度有上下限**：单个楼层承载超过约 3 类信息时拆层，主题相近的碎楼层合并；宁可楼层少而每层完整，不做堆砌式长页。

> 导航与页脚属站点框架：工程内代码按目标仓既有结构；单文件 DEMO 按目标站点实际结构还原，拿不到实际结构时向需求方索要，禁止编造。

### 第四步：楼层内组件选型

对每个楼层按内容形态从中观层选型表（下节）定承载方式，再下探控件级：具体控件（按钮 / 输入框 / 标签…）查 [component-cheatsheet.md](component-cheatsheet.md)。选型纪律：同类信息聚合优先选语义承载强的标准组件（结构化数据用 `ODataTable`、状态用 `OTag`，不用纯文本堆砌或手写 div 模拟结构化内容）。

## 典型页面范式表（五类）

| 页面类型 | 核心任务 | 典型楼层序列 | 组件倾向 |
|---------|---------|-------------|---------|
| 门户 / 落地页 | 汇总入口与亮点 | 导航 → Banner → 功能卡片栅格 → 数据统计 → 页脚 | `OCard` 栅格、`OButton`、`OTag` |
| 列表页 | 检索与浏览内容 | 导航 → 筛选栏 + 列表 → 分页 → 页脚 | `OInput` / `OSelect` + `ODataTable`（或卡片流）+ `OPagination` |
| 详情页 | 深读单条内容 | 导航 → 面包屑 → 标题区 → 正文 → 相关推荐 → 页脚 | `OBreadcrumb`、`OTag`、`OLink` |
| 表单 / 配置页 | 结构化输入 | 导航 → 表单区 → 操作区 → 页脚 | `OInput`、`OSelect`、`ORadioGroup`、`OButton` |
| 工作台 / 仪表盘 | 状态总览与快捷操作 | 导航 → 统计卡片 → 分区内容 → 页脚 | `OCard`、`OTab`、`OTag` |

> 范式不是模板：楼层序列按第一步的设计输入裁剪，每个楼层都要能回答「为什么在」（对应哪个功能编号 / 内容来源）。

范式实拍（合规代码示例）：功能楼层 + 卡片栅格见 [examples/feature-section.vue](examples/feature-section.vue)；带筛选的列表页见 [examples/list-filter-page.vue](examples/list-filter-page.vue)。

## 楼层级（中观层）选型表

| 楼层内容形态 | 承载方式 |
|-------------|---------|
| 重点宣告（版本发布 / 活动引导） | `OBanner` 或标题区（语义标签 + token） |
| 并列功能 / 特性 | `OCard` × N，24 栅格对齐 |
| 数据统计 | 自定义数字 + 描述（语义标签 + 响应式 token） |
| 结构化数据 | `ODataTable`（columns schema 风格） |
| 卡片式内容流 | `OCard` 列表 + `OPagination` |
| 同域分组浏览 | `OTab` / `OAnchor` 分区 |
| 纯布局容器（楼层壳、文字区块） | 语义化标签（`<section>` / `<header>` / `<div>`）+ scoped 样式，无需组件 |

## 信息密度与占位纪律

页面结构定了「放什么」，本节定「放多少、用什么占位」——生成时遵守，生成后进 [checklist.md](checklist.md) ⑤ 设计基本盘逐项核对：

1. **字号阶梯 ≤ 4 级**：页面标题 / 小节标题 / 正文 / 辅助说明四档封顶；同级元素同规格（重复原则），跨档用字号 / 字重 / 颜色至少一项拉开明确反差，不留「看起来差不多」的模糊层级。
2. **层级可数**：标题层级与楼层结构一一对应，锚点与内容一一对应。
3. **真实占位文案**：占位内容用贴合业务的中文真实语义（真实的产品名 / 参数 / 版本号），禁止 lorem ipsum 与「示例文本」式空洞占位——占位是为了可评审，空洞占位让评审失效。
4. **语义地标完整**：用 `<header>` / `<nav>` / `<main>` / `<footer>` 划分页面区块，核心内容置于 `<main>`。
5. **空态与异常路径有交代**：列表空、加载中 / 失败、无结果等非理想路径要给出占位说明或引导操作，不只画理想路径。
